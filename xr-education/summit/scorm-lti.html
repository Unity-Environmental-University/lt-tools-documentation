    SCORM courses and the Canvas LTI tool

    Summit can host Articulate Storyline courses (SCORM 1.2, SCORM 2004 or xAPI packages) and play them inside Canvas through its own LTI 1.3 tool. Canvas handles the roster and the gradebook. Summit keeps every answer, the time on each slide and question, every click, and a timeline of everything the course reported, under a pseudonym, in a database of its own. It shows all of it under Learning in the sidebar, as a section of its own.

    The feature is off until LEARNING_DATABASE_URL is set. Nothing changes for an instance that doesn't set it.

    How a launch works

    sequenceDiagram
    participant S as Student in Canvas
    participant C as Canvas
    participant T as Summit LTI tool
    participant P as Summit player
    participant DB as Learning database
    S->>C: Opens the assignment
    C->>T: OIDC login (/lti/login)
    T->>C: Redirect to Canvas authorize, with state and nonce
    C->>T: Signed id_token (/lti/launch)
    T->>DB: Placement, pseudonymous learner, attempt, launch
    T->>P: 303 to /learn/play?t=attempt token
    P->>P: scorm-again runtime, course in an iframe
    P->>DB: Commits (/api/learn/commit) and call trace (/api/learn/trace)
    T->>C: Score to the gradebook (AGS) when the attempt is finished
    • Placing a course: an instructor adds an assignment with submission type External Tool and picks Summit learning. Canvas opens Summit's package picker (LTI Deep Linking), and the choice is stored on the assignment as a custom package_id.
    • Playing it: the player page exposes the SCORM API on its window (API_1484_11 for 2004, API for 1.2) and loads the course from /learn/content/<token>/... on the same origin, so Storyline finds the API the usual way.
    • Authorisation: no cookies are used inside Canvas's iframe. The launch mints a short-lived attempt token (2 hours by default, renewed while the course is open). Commits and traces carry it, and course files carry a separate content token in their path. The dashboard API key never reaches the browser.
    • Resume: each commit stores the whole CMI tree. The next launch hands it back with cmi.entry set to resume when the course exited with suspend, so Storyline's resume prompt works.
    • xAPI courses: Summit is the course's record store (LRS). The player opens the course with endpoint, auth, actor, registration and activity_id in the query string, the way Storyline and Rise expect, and the course sends its statements and resume state to /api/learn/xapi/ (xAPI 1.0.3: statements, state and profile documents). The auth is the attempt token, and the actor is the learner's pseudonym, so a course can only write to its own attempt.
    • Grades: when an attempt is completed, passed or failed, Summit posts the score (0 to 100) to the assignment's line item. A score is sent again only when it changes. A failure is shown on the attempt page and retried on the next commit. Instructor test launches are never graded.

    What is stored, and where

    Everything lives in the learning database, not Summit's analytics database. It is not in the summit-backup dumps or in Summit's data export.

    Table Holds
    packages Uploaded courses; files live under LEARNING_PACKAGES_DIR
    placements Canvas assignment or link, course title, line item
    learners One row per person: HMAC-SHA256(LEARNING_PSEUDONYM_KEY, iss + sub)
    learner_vault The Canvas user id, AES-256-GCM sealed with LEARNING_VAULT_KEY; only read to send a grade
    attempts, attempt_launches Status, score, total time, each sitting
    cmi_state The latest CMI tree for resume
    interactions One row per answer: response, correct answer, result, latency, timestamps; for Storyline quizzes also the quiz, its take and the try at that question (source = 'player'). Reports read the answer_rows view.
    runtime_calls Every SetValue, Commit, Initialize, Terminate with a browser timestamp (a Timescale hypertable)
    xapi_statements, xapi_documents Every xAPI statement as sent, and the state and profile documents (resume)
    learning_events One timeline for every kind of course: slides with time on each, clicks (with position and label), answers, typing (length only), media, tab switches, status and score
    audit_log Who viewed or changed learning data
    lti_launch_log Each Canvas login and launch: step, result, reason, course and assignment titles. No user ids. Kept 90 days.

    The tool asks Canvas for anonymous privacy, so Canvas sends no names or email addresses. Learners show in the dashboard as the first 12 characters of their pseudonym. Typed free-text answers (fill-in, long-fill-in) are stored as [free text not stored] unless LEARNING_CAPTURE_FREE_TEXT=1.

    These are still education records under FERPA, because the vault and the pseudonym key can link them back to a student. Treat the learning database, its backups and the three keys accordingly, and check retention and access with the registrar before real students use it.

    What the analytics show

    The page watcher in the player sees the course page directly (it is served from Summit's own origin): which Storyline slide is showing, what the learner clicks and where, how much they type (never what), media play and pause, and when they leave the tab. SCORM calls and xAPI statements add answers, status and score. All of it lands in learning_events.

    Storyline quizzes are read from the page too. A Storyline course reports its answers and score to the LMS only when its tracking is tied to a quiz result slide. Courses published to "track using completion trigger" send nothing about the quiz, so SCORM alone shows no answers. The watcher listens to Storyline's own quiz events (interaction:evaluated on every submit, quiz:completed when a take is finished), which fire whatever the tracking setting is. Each submit is stored with the text of the choice the learner picked (read from the slide, not Storyline's "Choice A"), the correct answer, right or wrong, which try at that question it was, and which take of the quiz. Each finished take stores its score, percent and pass or fail. When a course sends its own answers as well, the player's copy is the one reports use, so nothing is counted twice. Free-text answers are never sent from the page, only their length.

    • Overview: learners, attempts, answers, slide views, clicks, median time, 30 days of activity, and a card per course.
    • Course page: completion and pass rates; a slide funnel (how many attempts reached each slide, median and average time, where unfinished attempts stopped); a card per question with the share of each answer, correct rate, right-first-try rate and median time to answer; a click map per slide and the most clicked objects; each learner's progress, answers and quiz takes. CSV exports of every event and every answer.
    • Attempt page: time on each slide, each quiz take (right first try, wrong submits, result), every submit next to the correct answer with its try and take, the click map, the full timeline, and the raw SCORM calls or xAPI statements.

    Settings

    Variable Needed Meaning
    LEARNING_DATABASE_URL yes The separate learning database. Unset turns the feature off.
    LEARNING_PSEUDONYM_KEY yes 32 bytes, base64 or hex. Changing it gives every learner a new pseudonym.
    LEARNING_VAULT_KEY yes 32 bytes. Losing it means grades can't be sent for existing learners.
    LEARNING_TOKEN_SECRET yes 32 bytes. Signs attempt, content and deep-link tokens.
    SUMMIT_PUBLIC_URL yes Public https URL including the basePath, such as https://example.edu/summit.
    LTI_CLIENT_ID yes The Canvas developer key's client id.
    LTI_TOOL_PRIVATE_KEY yes RSA private key (PEM, \n escapes allowed). Its public half is served at /lti/jwks.
    LTI_PLATFORM_ISSUER no https://canvas.instructure.com (default). Test and beta instances use https://canvas.test.instructure.com and https://canvas.beta.instructure.com.
    LTI_DEPLOYMENT_IDS no Comma-separated deployment ids to accept. Empty accepts any deployment of the client id.
    LTI_AUTH_LOGIN_URL, LTI_AUTH_TOKEN_URL, LTI_JWKS_URL no Follow the issuer: sso.canvaslms.com for production, sso.test.canvaslms.com or sso.beta.canvaslms.com for the test and beta instances. Set them only for a self-hosted Canvas.
    LTI_TOKEN_AUDIENCE no aud of the grade-token request. Defaults to the token URL.
    LTI_TOOL_KEY_ID no kid of the tool key, summit-1 by default.
    LTI_FRAME_ANCESTORS no Who may frame the player. Default 'self' https://*.instructure.com https://*.canvaslms.com.
    LEARNING_PACKAGES_DIR no Where unpacked courses live. /data/learning-packages in compose.
    LEARNING_MAX_PACKAGE_MB no Upload limit, 1024 by default.
    LEARNING_ATTEMPT_TOKEN_TTL_SECONDS, LEARNING_CONTENT_TOKEN_TTL_SECONDS no Token lifetimes, 2 hours and 12 hours.
    LEARNING_CAPTURE_FREE_TEXT no 1 keeps typed answers.
    LEARNING_ALLOW_COURSE_CONNECTIONS no 1 lets course pages connect to other sites. Off, they can only reach Summit, which also blocks Storyline's own telemetry to metrics.articulate.com.
    LEARNING_DEMO_MODE no 1 turns on Try a course: play any course as a made-up demo learner without Canvas. For local demos only.

    Generate the keys once per environment:

    cd dashboard && npm run learning:keys

    Set it up

    1. Start the learning database. With compose, set LEARNING_DB_PASSWORD and LEARNING_DATABASE_URL in .env, then run docker compose --profile learning up -d. It has its own volume and is not mounted into the backup sidecar. The production deploy script runs plain docker compose up -d --build, so there set COMPOSE_PROFILES=learning alongside the other secrets (Infisical, /summit) and the profile is picked up.
    2. Set the keys and URLs above in .env. The dashboard container applies the learning migrations on start (npm run migrate:learning does the same by hand).
    3. Give people access. Admins can see learning data. Anyone else needs Settings, Accounts, Allow learning data.
    4. Create the Canvas developer key (Canvas admin): Admin, Developer Keys, Developer Key, LTI Key. Choose Enter URL and paste SUMMIT_PUBLIC_URL/lti/config. Set the redirect URI to SUMMIT_PUBLIC_URL/lti/launch. Save it, switch it on and copy the client id into LTI_CLIENT_ID.
    5. Install the app in a sub-account or course: Settings, Apps, View App Configurations, + App, By Client ID. Copy the deployment id into LTI_DEPLOYMENT_IDS if you want to restrict it.
    6. Upload a course. In Storyline, publish for LMS as SCORM 2004 (3rd or 4th edition) and upload the zip under Learning in the Summit sidebar.
    7. Place it. In Canvas, create an assignment, set the submission type to External Tool, find Summit learning and pick the course. Set the points.

    Learning, Canvas in the dashboard checks each of these settings, lists the values to hand the Canvas admin, and has a Check the connection to Canvas button. It fetches Canvas's signing keys, fetches Summit's own key set through the public address, and asks Canvas for a grade token. That token only comes back once the developer key is on and points at this server, so a pass there means launches and grades will work.

    Testing in a dev course

    For the full walkthrough, including every Infisical secret, see Setting up the Canvas LTI tool.

    A sandbox course in the real Canvas is the usual place: it uses the production issuer, and Student View gives a test student whose grades go to the gradebook like anyone's.

    1. Deploy Summit with Learning on (the settings above), reachable over https from the internet. If the reverse proxy limits request size, raise it for /summit/api/learning/packages so course zips can be uploaded (nginx: client_max_body_size 1024m).
    2. Open Learning, Canvas. Fix anything marked Fix, except the client id.
    3. Ask the Canvas admin for a developer key. Send them the JSON URL and Redirect URI from that page. They create it with Enter URL, switch it on and send back the client id. Put it in LTI_CLIENT_ID and redeploy.
    4. Check the connection to Canvas. All three should pass.
    5. Install it in the dev course: Settings, Apps, View App Configurations,
    6. App, By Client ID. Course admins or teachers can do this if the account allows it; otherwise the admin installs it in a sub-account.
    7. Upload a course and place it (Courses tab, then a Canvas assignment with External Tool and Summit learning).
    8. Play it as a student. Use Student View, or a test account enrolled as a student. The launch appears under Recent launches, the attempt under the course's analytics, and the score in the Canvas gradebook. Launches by teachers and designers are kept but marked instructor: they get no grade and stay out of the statistics.

    When a launch fails, Recent launches on the Canvas tab says which step and why, without user ids. Common first-launch problems:

    What you see Cause
    A login with no launch after it The developer key's Redirect URIs don't include SUMMIT_PUBLIC_URL/lti/launch, or the key is off. Canvas shows its own error and never posts back.
    issuer ... is not LTI_PLATFORM_ISSUER A test or beta Canvas instance; set LTI_PLATFORM_ISSUER to match.
    client id ... is not LTI_CLIENT_ID The key was recreated; copy the new client id.
    deployment ... is not in LTI_DEPLOYMENT_IDS Installed somewhere new; add the id or empty the setting.
    login state unknown, expired or already used The launch took over 10 minutes, or a page was reloaded mid-launch. Open the assignment again.
    The tool's page refuses to show inside Canvas Canvas on its own domain; add it to LTI_FRAME_ANCESTORS.
    Grades listed under Grades that didn't reach Canvas Canvas's answer is shown beside each. Fix the cause and select Resend.

    Demo on your own machine

    tools/learning-demo runs Summit with Learning and demo mode on, in Docker, with its own two databases. Put course zips in tools/learning-demo/packages/ and run:

    tools/learning-demo/run.sh

    It prints the address (http://localhost:3300/summit/dashboard/learning) and a generated admin password. Try a course plays a course as demo learner A, B or C, with what Summit records shown live beside it. See tools/learning-demo/README.md, including sharing it on your tailnet with tailscale serve.

    Try it locally

    tools/learning-e2e runs the whole flow against a fake Canvas: upload, deep linking, a learner launch, a real headless Chromium answering the sample quiz, the database contents, the score Canvas receives, resume on relaunch and the dashboard pages.

    # A local TimescaleDB, user and password summit, on port 5432
docker run -d --name summit-learning-test -p 5432:5432 \
  -e POSTGRES_USER=summit -e POSTGRES_PASSWORD=summit -e POSTGRES_DB=summit \
  timescale/timescaledb:latest-pg16
psql postgres://summit:summit@localhost:5432/summit -c "CREATE DATABASE summit_main_e2e" -c "CREATE DATABASE summit_learning_e2e"

cd dashboard && npm ci && npm run build
DATABASE_URL=postgres://summit:summit@localhost:5432/summit_main_e2e npm run migrate
LEARNING_DATABASE_URL=postgres://summit:summit@localhost:5432/summit_learning_e2e npm run migrate:learning

cd ../tools/learning-e2e && npm install
npx playwright install chromium   # on macOS; Linux uses the bundled build
npm run setup             # throwaway keys and server env
npm run canvas &          # fake Canvas on :3199
npm run server &          # Summit on :3100
npm test

    Limits and open questions

    • One SCO per package. Storyline publishes one, which is the common case. Multi-SCO packages play only their first launchable item, and SCORM 2004 sequencing is not implemented.
    • cmi5 packages are refused. xAPI (Tin Can) packages play against Summit's own record store; cmi5's launch and session rules aren't done.
    • xAPI answers depend on the course. Storyline sends an answered statement per question with the response and result; Summit reads those. Other tools' statements are kept whole, but may need mapping to show as answers.
    • Slides are read from Storyline's player. Other tools still get clicks, typing, media and tab switches, but their slides come only from what the course reports.
    • Login state is checked on the server only. It is single use and expires in 10 minutes, but it is not tied to the browser with a cookie, because cookies are unreliable in Canvas's iframe. The LTI platform storage (postMessage) flow would close this; it's a follow-up.
    • Tokens ride in URLs. The commit beacon sent on page close can't carry headers, so the attempt token is in the query string. Pages send Referrer-Policy: no-referrer (same-origin for course files), and tokens are short-lived, but they can appear in reverse-proxy access logs. Consider stripping query strings from those logs.
    • Course files are served by Next.js. That is fine for typical courses. For large video, serve LEARNING_PACKAGES_DIR from the reverse proxy instead.
    • Not yet tried against a real Canvas. The flow follows Canvas's LTI 1.3 documentation and passes the local run above, but the first real launch is where surprises show up. The Canvas tab's launch log is there to catch them.
    • Analytics are per course package, not per Canvas course. If the same package is placed in a dev course and a real one, their learners are counted together. The Canvas tab shows each assignment's own counts.
